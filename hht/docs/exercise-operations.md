# 演習運営手順

## 1. 配布

受講者ごとに、このリポジトリ全体のコピーまたは作業ブランチを用意します。授業では毎回、VS Codeの「フォルダーを開く」でリポジトリのルートを開きます。`starter-site`だけを別ワークスペースで開かせません。共有の`main`や教材原本を直接編集させず、依頼メールは授業回に合わせて1通ずつ案内します。

開始時の確認:

1. VS Codeのエクスプローラーにルートの`README.md`と`hht`が見える。
2. ソース管理に受講者本人のブランチまたは個人コピーが表示される。
3. `hht/lessons`から今日の授業パックを開ける。
4. `hht/starter-site`、`hht/fixtures`、`hht/docs`を同じワークスペースから参照できる。
5. 前回終了時の変更状態と、今回の開始バージョンを確認できる。

画像素材の出自と用途は `fixtures/photographer-delivery/ASSET-MANIFEST.md` を参照します。本教材の「模擬撮影納品」は実際のカメラマン撮影ではなく、依頼・検収・権利確認を学ぶための生成素材です。実在の撮影者名や権利情報を捏造しません。

## 2. 第1回で作る自習環境

第1回で、編集からデプロイ、バックアップ、復元までを一度通します。以後の自習では同じ手順を繰り返し、授業外でも「変更したが表示方法が分からない」「失敗が怖くて試せない」という状態を減らします。

1. 受講者用に用意されたリポジトリの`hht/starter-site`を編集対象として確認する。
2. 作業開始前を「開始時点」としてバージョン記録へ残す。学校環境でGitを使える場合は受講者ブランチのコミット、使えない場合は日時・名前付きの読み取り専用バックアップとする。
3. ローカルHTTPサーバーで表示し、編集、保存、再読み込みを試す。
4. `practice-server/staging` または受講者ごとに分離した練習URLへ、対象ファイルだけをデプロイする。
5. 公開URLをブラウザで確認し、URLと確認時刻を記録する。
6. 小さな変更を1件加え、2番の状態へ復元する。
7. 「作業を開く → 編集 → 確認 → バージョン記録 → デプロイ」の自習再開手順をワークブックへ書く。

本番サーバー、実在サイト、共有メール領域は第1回の対象にしません。認証情報を使う場合は講師が用意した受講者別の練習領域に限定します。

## 3. ブラウザ確認

ローカルファイルとして開く方法とローカルHTTPサーバーで開く方法を区別します。講師環境で利用できる場合は、`starter-site` をルートに静的サーバーを起動します。

確認する画面幅の目安:

- 約320px: 小さいスマートフォン相当
- 約768px: タブレット相当
- 1280px以上: デスクトップ相当
- 200%拡大: 幅を保ったままの文字拡大確認

端末名に合わせることより、内容の折返し・読み順・操作が破綻しないかを優先します。

## 4. 第12〜15回の画像演習

1. `hero-ai-master.png` をAI生成の元候補として評価する。
2. `simulated-shoot-001.jpg` を模擬撮影納品として検収する。
3. `ASSET-MANIFEST.md` で出自、用途、制限を確認する。
4. 元画像を上書きせず、目的別の出力を作る。
5. 画質、ピクセル寸法、ファイル容量、形式を比較表にする。
6. `starter-site/images/hero-cafe.webp` を実装候補として使用する。
7. CSSの背景画像だけで情報を伝えない。装飾扱いか情報画像かを判断する。
8. PC・スマホのトリミング、文字のコントラスト、読み込み時の見え方を確認する。

## 5. 模擬クライアント確認

受講者は確認依頼に、確認対象、変更内容と対象外、特に見てほしい点、未確定事項、確認期限、「公開可」と明示してほしい旨を含めます。

講師は不足がある場合、承認せず具体的な不足を一つだけ返します。承認後、受講者は変更記録の状態を「依頼中」から「承認済み」へ更新します。

## 6. 公開演習の段階

第1回で段階Cの基本操作を体験します。その後は各回の確認用デプロイで繰り返し、第15回に承認済み成果物の最終公開と公開後確認を行います。段階B・Aは授業環境と権限が用意できた場合だけ実施します。

### 段階C: 模擬公開

1. `practice-server/production` の現状を `practice-server/backups/日時` へ複製する。
2. 承認済みファイルだけを `practice-server/staging` へ配置する。
3. ステージング相当をブラウザで確認する。
4. 公開判定表がすべてPASSか、理由付きNOT APPLICABLEであることを確認する。
5. 承認済みファイルだけを `practice-server/production` へ配置する。
6. 公開相当URLを再確認し、時刻、担当、対象、結果を記録する。
7. 意図的な不具合演習では、バックアップから対象ファイルだけを戻す。

フォルダー全体の無条件コピーは使いません。アップロード対象一覧と実ファイルを照合します。

### 段階B: 講師用ステージングへSFTP

1. 講師が受講者ごとに接続先とアップロード可能なフォルダーを限定する。
2. ホスト鍵、接続先、ユーザー名、ポート、リモートパスを接続票と照合する。
3. 認証情報をソース、提出物、チャット、画面共有へ含めない。
4. 空のテストファイルで接続先を確認してから、承認済みファイルだけを転送する。
5. ブラウザで確認し、転送記録を残す。

### 段階A: XServerでSSH・SFTP

XServerのSSHは公開鍵認証を使用し、公式マニュアル記載の接続ポートやサーバー設定を開講時に確認します。SSH操作は誤るとWebやメールへ影響するため、講師が分離した練習用領域だけで行います。

1. サーバーパネルでSSHを有効化し、練習用の鍵と接続対象を準備する。
2. 秘密鍵の保存場所、アクセス権、共有禁止を確認する。
3. `pwd` とディレクトリ一覧で現在位置を確認し、公開先を絶対パスで記録する。
4. 現在の公開ファイルを別の明示的なバックアップ先へ保存する。
5. SFTPで対象ファイルだけをステージング相当領域へ転送する。
6. 承認後、本番相当領域へ限定反映する。
7. HTTP表示、リンク、更新日時、差分を確認する。
8. 失敗時は対象ファイルだけをバックアップから戻す。

SSHで削除・一括移動・権限変更を行う演習は、専用の空フォルダー以外では実施しません。

## 7. 完成版の扱い

講師は一つの唯一解を先に配布しません。受講者の変更が依頼、アクセシビリティ、レスポンシブ、権利、公開条件を満たしているかをルーブリックで判定します。
