# 演習運営手順

## 1. 配布

受講者は[共通のクローン手順](./workbook/common.md#clone-edu)で、`hgsk/edu`を本人のDocumentsへ取得します。  
授業では`Documents/edu`を開きます。  
授業では毎回、PCのVS Codeで本人用のローカルGitリポジトリを開き、リポジトリのルートを開きます。  
`starter-site`だけを別ワークスペースで開かせません。  
共有の`main`や教材原本を直接編集させず、依頼メールは授業回に合わせて1通ずつ案内します。

開始時の確認:

1. VS Codeのエクスプローラーにルートの`README.md`と`hht`が見える。
2. ソース管理に受講者本人のブランチまたは個人コピーが表示される。
3. `hht/lessons`から今日の授業パックを開ける。
4. `hht/starter-site`、`hht/fixtures`、`hht/docs`を同じワークスペースから参照できる。
5. 今回の作業フォルダーと、開始データの内容を確認できる。

### 各回の独立した開始データ

全15回の開始データは、それぞれ`hht/lessons/NN/start`に保存しています。  
準備コマンドと再開方法の正本は[共通の開始手順](./workbook/common.md#independent-day-start)です。  
受講者は`hht/practice/dayNN`で作業し、開始状態と変更を同じローカルGitへ記録します。  
他のDAYの成果を移行させたり、欠席回の完成物を先に作らせたりしません。  
配布前に教材検査を実行し、開始データのファイル・ハッシュ・参照先が一致することを確認します。


## 2. 第1回で作る自習環境

第1回で、編集からデプロイ、バックアップ、復元までを一度通します。  
以後の自習では同じ手順を繰り返し、授業外でも「変更したが表示方法が分からない」「失敗が怖くて試せない」という状態を減らします。

1. 準備した`hht/practice/dayNN`を編集対象として確認する。
2. 作業開始前を「開始時点」としてバージョン記録へ残す。  
   本人用の教材フォルダーで、配布状態のコミットを残す。
3. PCのローカルHTTPサーバーをブラウザで表示し、編集、保存、再読み込みを試す。
4. `practice-server/staging` または受講者ごとに分離した練習URLへ、対象ファイルだけをデプロイする。
5. 公開URLをブラウザで確認し、URLと確認時刻を記録する。
6. 小さな変更を1件加え、2番の状態へ復元する。
7. 「作業を開く → 編集 → 確認 → バージョン記録 → デプロイ」の自習再開手順をワークブックへ書く。

本番サーバー、実在サイト、共有メール領域は第1回の対象にしません。  
認証情報を使う場合は講師が用意した受講者別の練習領域に限定します。

## 3. ブラウザ確認

ローカルファイルとして開く方法とローカルHTTPサーバーで開く方法を区別します。  
講師環境で利用できる場合は、そのDAYの`hht/practice/dayNN`をルートに静的サーバーを起動します。

確認する画面幅の目安:

- 約320px: 小さいスマートフォン相当
- 約768px: タブレット相当
- 1280px以上: デスクトップ相当
- 200%拡大: 幅を保ったままの文字拡大確認

端末名に合わせることより、内容の折返し・読み順・操作が破綻しないかを優先します。

## 4. 第12〜15回の画像演習

1. `hero-ai-master.png` をAI生成の元候補として評価する。
2. `simulated-shoot-001.jpg` を模擬撮影納品として検収する。
3. `ASSET-MANIFEST.md` で出自、用途、制限を確認する。
4. 元画像を上書きせず、目的別の出力を作る。
5. 画質、ピクセル寸法、ファイル容量、形式を比較表にする。
6. そのDAYの`images/hero-cafe.webp`を実装候補として使用する。
7. CSSの背景画像だけで情報を伝えない。  
   装飾扱いか情報画像かを判断する。
8. PC・スマホのトリミング、文字のコントラスト、読み込み時の見え方を確認する。

## 5. 模擬クライアント確認

受講者は確認依頼に、確認対象、変更内容と対象外、特に見てほしい点、未確定事項、確認期限、「公開可」と明示してほしい旨を含めます。

講師は不足がある場合、承認せず具体的な不足を一つだけ返します。  
承認後、受講者は変更記録の状態を「依頼中」から「承認済み」へ更新します。

## 6. 公開演習の段階

第1回で段階Cの基本操作を体験します。  
その後は各回の確認用デプロイで繰り返し、第15回に承認済み成果物の最終公開と公開後確認を行います。  
段階B・Aは授業環境と権限が用意できた場合だけ実施します。

### 段階C: 模擬公開

1. `practice-server/production` の現状を `practice-server/backups/日時` へ複製する。
2. 承認済みファイルだけを `practice-server/staging` へ配置する。
3. ステージング相当をブラウザで確認する。
4. 公開判定表がすべてPASSか、理由付きNOT APPLICABLEであることを確認する。
5. 承認済みファイルだけを `practice-server/production` へ配置する。
6. 公開相当URLを再確認し、時刻、担当、対象、結果を記録する。
7. 意図的な不具合演習では、バックアップから対象ファイルだけを戻す。

フォルダー全体の無条件コピーは使いません。  
アップロード対象一覧と実ファイルを照合します。

### 段階B: 講師用ステージングへSFTP

1. 講師が受講者ごとに接続先とアップロード可能なフォルダーを限定する。
2. ホスト鍵、接続先、ユーザー名、ポート、リモートパスを接続票と照合する。
4. 空のテストファイルで接続先を確認してから、承認済みファイルだけを転送する。
5. ブラウザで確認し、転送記録を残す。

### 段階A: 講師のAzure VMでSSH・SCP・SFTP

講師が[Azure VM公開演習](./azure-practice.md)の手順で既存のUbuntu VMに受講者別アカウントを作り、PCのターミナルから公開鍵認証で接続します。  
接続先IP、ホスト鍵、対象パスを確認してから操作します。

1. PCのターミナルで練習用の鍵を作り、講師が受講者用アカウントを追加する。
2. 秘密鍵の保存場所、アクセス権、共有禁止を確認する。
3. `pwd` とディレクトリ一覧で現在位置を確認し、公開先を絶対パスで記録する。
4. 現在の公開ファイルを別の明示的なバックアップ先へ保存する。
5. SCPとSFTPで対象ファイルだけを `/srv/hht-public/受講者ID/` へ転送する。
6. 承認後、同じ受講者用公開フォルダーへ限定反映する。
7. ApacheのHTTP表示、リンク、更新日時、差分を確認する。
8. 失敗時は対象ファイルだけをバックアップから戻す。

SSHで削除・一括移動・権限変更を行う演習は、専用の空フォルダー以外では実施しません。  
VMの停止・削除は講師が費用と他の受講者の利用状況を確認して行います。

## 7. 完成版の扱い

講師は一つの唯一解を先に配布しません。  
受講者の変更が依頼、アクセシビリティ、レスポンシブ、権利、公開条件を満たしているかをルーブリックで判定します。
