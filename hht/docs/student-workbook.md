# 新人Webデザイナー お仕事ワークブック

今日からあなたは、架空のカフェ **「NORTH LIGHT COFFEE」** を担当する新人Webデザイナーです。

このワークブックでは、毎回お客さまから届く依頼を読み、必要なHTML・CSSを学びながら、実際のWeb制作に近い流れで仕事を進めます。

大切なのは、**きれいなページを作ることだけではありません。**

- 依頼を正しく読む
- 分からないことを質問する
- 変更してよい場所と、してはいけない場所を分ける
- 小さく変更して確認する
- 作業内容を自分の言葉で報告する

ここまでできて、1つの仕事が完了です。

---

## このワークブックのゴール

15回の授業が終わるころには、次のことを一人で進められることを目指します。

1. Web制作の依頼内容を読み取れる
2. HTML・CSSを使って必要な修正ができる
3. パソコンとスマートフォンの両方で確認できる
4. 修正前と修正後の違いを説明できる
5. 分からないことを質問できる
6. GitHubに作業を残せる
7. 自分の制作物をポートフォリオとして紹介できる

---

## STEP 1　作業場所と依頼を確認する

CodespacesまたはVS Codeで **リポジトリのルート** を開きます。左側に README.md と hht が見えることを確認してください。

次に、ソース管理画面で **自分用のコピーまたは自分の作業ブランチ** を使っていることを確認します。共有教材のmainを直接編集しません。

依頼から次をメモします。

- Fromはだれか
- Toはだれか
- CCはだれか
- 頼まれていること
- まだ分からないこと
- DAY 1では依頼された文章そのものは変更しないこと

## STEP 2　現在のサイトをローカルで表示する

VS Codeのターミナルを開き、リポジトリのルートで次を実行します。

~~~bash
python -m http.server 8000 --directory hht/starter-site
~~~

### Codespacesの場合

1. 画面下部の **PORTS** を開く
2. ポート8000を探す
3. **Open in Browser** を押す
4. PORTSに表示された **Forwarded Address** を使う

Forwarded AddressはCodespaceごとに異なります。教材に書かれていないURLを自分で作らないでください。

### PC上のVS Codeの場合

ブラウザで次を開きます。

~~~text
http://localhost:8000/
~~~

「Address already in use」と出た場合は8001など空いている番号へ変え、ブラウザ側も同じ番号にします。

表示できたら、トップページ、画像、メニューへのリンク、店舗案内へのリンクを確認します。

## STEP 3　開発者ツールで「一時変更」を体験する

[はじめてのブラウザ開発者ツール](./devtools-first-lesson.md)を開き、次を実行します。

1. Elementsでh1を選ぶ
2. h1の文字を一時的に変更する
3. Stylesでcolorまたはfont-sizeを一時的に変更する
4. 再読み込みし、元へ戻ることを確認する
5. 画面幅を375pxにする
6. Consoleに赤いエラーがないか確認する

ここでの変更はHTMLファイルには保存されません。

hht/submissions/day-01/WORKLOG.md の「確認したこと」へ、次のように結果を残します。

~~~text
DevTools: h1確認 / CSS確認 / 375px確認 / Console: エラーなし
~~~

エラーがある場合は「エラーなし」と書かず、最初の1件のメッセージを記録します。

## STEP 4　開始時点を記録し、復元用コピーを作る

別のターミナルを開き、次を実行します。

~~~bash
git status --short
git rev-parse --short HEAD
~~~

2行目に表示された文字列が **開始バージョンID** です。WORKLOG.mdへ記録してください。

次に、表示された開始バージョンIDを使って復元用フォルダーを作ります。以下の <開始ID> を実際のIDへ置き換えます。

~~~bash
mkdir -p hht/practice-server/backups/day-01-<開始ID>
cp hht/starter-site/index.html hht/practice-server/backups/day-01-<開始ID>/index.html
~~~

このコピーは、模擬公開側を戻す練習に使います。

## STEP 5　HTMLを1か所だけ変更する

hht/starter-site/index.html を開き、h1を次のように **DAY 1の練習用** に変更します。

変更前:

~~~html
<h1>一杯から、街の日常をあたためる。</h1>
~~~

変更後:

~~~html
<h1>DAY1練習：一杯から、街の日常をあたためる。</h1>
~~~

保存し、STEP 2で開いたローカルページを再読み込みします。

- 「DAY1練習：」が表示される
- CSSが壊れていない
- メニューと店舗案内へのリンクが動く

ことを確認します。

## STEP 6　変更後のバージョンを残す

変更したHTMLだけをコミットします。

~~~bash
git add hht/starter-site/index.html
git commit -m "DAY1: practice HTML change"
git rev-parse --short HEAD
~~~

最後に表示された文字列が **変更後バージョンID** です。WORKLOG.mdへ記録します。

git commitで「nothing to commit」と出た場合は、index.htmlを保存できているか確認します。Gitの利用自体ができない環境では、[完成条件の「困ったとき」](../student/assignment-checks.md#day-1-環境デプロイ復元)にある日時付きバックアップ方式を使います。

## STEP 7　練習公開する

### A. 学校から練習用URLと接続方法が配布されている場合

配布された接続票や手順だけを使います。そこに書かれていないホスト名、パス、ユーザー名、パスワードを推測しません。

公開後、実際にブラウザで開いたURLをWORKLOG.mdの「確認URL」へ記録します。

### B. 練習用URLが配布されていない場合（この教材の標準手順）

practice-server/staging を **模擬公開先** にします。最初だけ、ページ表示に必要なファイルを明示して配置します。

~~~bash
mkdir -p hht/practice-server/staging/css hht/practice-server/staging/images
cp hht/starter-site/index.html hht/starter-site/menu.html hht/starter-site/about.html hht/practice-server/staging/
cp hht/starter-site/css/style.css hht/practice-server/staging/css/
cp hht/starter-site/images/hero-cafe.webp hht/practice-server/staging/images/
~~~

フォルダー全体を無条件に上書きせず、何を公開したか分かるようにファイルを指定しています。

次に、別のターミナルで模擬公開先を表示します。

~~~bash
python -m http.server 8001 --directory hht/practice-server/staging
~~~

CodespacesではPORTSの8001から **Open in Browser** を押し、表示されたForwarded Addressを使います。PC上のVS Codeでは http://localhost:8001/ を開きます。

このURLで「DAY1練習：」が表示されることを確認し、WORKLOG.mdには **模擬公開URL** として実際に開いたURLを記録します。

## STEP 8　ソースを開始時点へ戻し、変更後へ戻す

STEP 4で記録した開始バージョンIDを使います。<開始ID> を実際のIDへ置き換えてください。

~~~bash
git restore --source=<開始ID> -- hht/starter-site/index.html
~~~

ローカルページを再読み込みし、「DAY1練習：」が消えたことを確認します。

確認できたら、変更後コミットの内容へ戻します。

~~~bash
git restore --source=HEAD -- hht/starter-site/index.html
~~~

再読み込みし、「DAY1練習：」が再び表示されたことを確認します。

これで **変更前へ戻せる / 変更後へ戻せる** ことを確認できました。

## STEP 9　模擬公開先も一度戻す

STEP 7でBの模擬公開を使った人だけ行います。

<開始ID> を実際の開始バージョンIDへ置き換えます。

~~~bash
cp hht/practice-server/backups/day-01-<開始ID>/index.html hht/practice-server/staging/index.html
~~~

模擬公開URLを再読み込みし、「DAY1練習：」が消えたことを確認します。

次に、現在の変更後HTMLをもう一度配置します。

~~~bash
cp hht/starter-site/index.html hht/practice-server/staging/index.html
~~~

再読み込みし、「DAY1練習：」が戻ったことを確認します。

この **戻した画面 / もう一度反映した画面** を復元記録として残します。

## STEP 10　WORKLOGと受領返信を完成させる

[提出フォルダーの使い方](../submissions/README.md)に従い、hht/submissions/day-01/WORKLOG.md を作ります。

最低限、次を埋めます。

~~~md
# DAY 1 作業記録
- 依頼: 「創業10年」の文章修正依頼を受領。DAY 1では環境確認と復元練習まで実施
- 質問:
- 変更した場所: hht/starter-site/index.html のh1（DAY 1練習）
- 変更しなかった場所: 依頼された「創業10年」の本文
- 確認したこと: DevTools / 375px / Console / ローカル表示 / 練習公開 / 復元
- 未確認:
- バージョン: 開始=<開始ID> / 変更後=<変更後ID>
- 確認URL: <実際に開いた練習用URLまたは模擬公開URL>
~~~

最後に、受領返信の下書きを3文程度で作ります。

含める内容:

- 依頼を受け取ったこと
- 現在のサイトと確認用URLを確認できたこと
- 文章修正に入る前に確認したい点があること

パスワード、秘密鍵、Cookie、個人用トークンはWORKLOG、スクリーンショット、返信文へ入れません。

# DAY 3 ボタンのデザインをそろえて

> **佐藤さんからの依頼**  
> ページによって「メニューを見る」ボタンの色や形が違います。同じデザインにそろえられますか？

## 今日の目的

同じ役割のパーツに、同じCSSを使う考え方を学びます。

1か所ずつ別のCSSを書くのではなく、**共通の名前を付けて使い回す**ことがポイントです。

## 今日のゴール

- 同じ役割のボタンを探す
- classを使って共通の見た目にする
- CSSを別ファイルにまとめる
- 変更前後をブラウザで比較する

## STEP 1　対象のボタンを探す

3ページを開き、「メニューを見る」ボタンを探します。

現在の違いをメモします。

- 色
- 文字サイズ
- 角の丸さ
- 余白
- 横幅

## STEP 2　共通にする内容を決める

全部同じにするのか、一部だけ同じにするのかを考えます。

例:

- 色は同じ
- 角の丸さも同じ
- 横幅はページによって違ってよい

## STEP 3　classを付ける

何度も使うスタイルにはclassを使います。

idとの違いも確認します。

- id: 基本的に1か所だけ
- class: 同じ役割の複数要素に使える

## STEP 4　CSSを書く

共通のclassに対してCSSを書きます。

まず小さな変更から始めて、1つずつブラウザで確認します。

## STEP 5　3ページを比較する

すべての対象ページを開いて、ボタンの見た目がそろったか確認します。

## STEP 6　報告する

- どのページを変更したか
- 何を共通化したか
- まだ確認してほしい点

を書きます。

## 完了チェック

- [ ] 対象ボタンを全部確認した
- [ ] classを使った
- [ ] CSSを別ファイルに書いた
- [ ] 3ページをブラウザで比較した
- [ ] 文字が読みにくくなっていない
- [ ] 変更内容を報告した

# DAY 5 全ページの上と下をそろえて

> **佐藤さんからの依頼**  
> どのページを見ても同じメニューから移動できるようにしてください。

## 今日の目的

## 今日のゴール

- ヘッダーとフッターをそろえる

# 困ったときの順番

分からなくなったら、すぐに全部やり直すのではなく、次の順番で確認します。

1. 依頼文をもう一度読む
2. 今日のゴールを見る
3. 今どのSTEPか確認する
4. 変更前と変更後を比べる
5. ブラウザを再読み込みする
6. エラーメッセージを読む
7. クラスメイトや講師に「どこまでできたか」を伝えて質問する

質問するときは、

~~~text
○○をしようとしています。
△△まではできました。
□□のところで、××という表示になっています。
~~~

のように伝えると、原因を一緒に探しやすくなります。

# 最後に

このワークブックで一番大切なのは、HTMLやCSSの命令をたくさん暗記することではありません。

**依頼を読む → 考える → 作る → 確認する → 伝える**

この流れを、自分で繰り返せるようになることです。

分からないことがあっても問題ありません。  
分からないまま進めず、確認してから仕事を続けられることも、Webデザイナーに必要な力です。
