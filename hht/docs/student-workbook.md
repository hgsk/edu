# 新人Webデザイナー お仕事ワークブック

今日からあなたは、架空のカフェ「NORTH LIGHT COFFEE」を担当する新人Webデザイナーです。毎回、お客さまから新しい依頼が届きます。分からないことは質問して大丈夫。必要なHTML・CSSをその場で覚え、最後は自分の言葉で作業を報告しましょう。

## 前書き：まず意味を整える。見せ方は後から変えられる

**マークアップをする目的は、文章を意味のまとまりで整理し、人にもコンピューターにも内容の役目が伝わるようにすることです。** 先に「題名」「営業時間」「アクセス」「紹介文」をはっきりさせると、後からCSSで色・余白・配置を変えても、何の情報かを保てます。

![意味ごとに整理し、HTMLで役目を示し、CSSで見せ方を変える流れ。同じ営業時間とアクセスの構造から、縦に並べる表現と横に並べる表現を選べる説明図](../assets/day34/markup-purpose.svg)

### なぜ整理が必要？

情報があっても、まとまりや順番が分からないと、相手は答えを探すために何度も読み直すことになります。

- **メモ書き：** 北海道札幌市北区北00条西0丁目（架空）／水曜／18:30ラストオーダー／10:00〜19:00。数字や曜日が何の情報かを、その都度考える。
- **文章：** お店は札幌にあります。水曜日は休みです。ラストオーダーは18:30です。住所は北海道札幌市北区北00条西0丁目（架空）です。営業時間は10:00〜19:00です。時間と場所の話が行き来し、欲しい情報を拾いにくい。
- **会話：** 「住所はどこ？」「札幌です。水曜は休みで、ラストオーダーは18:30です」「住所は？」「北00条西0丁目です。あ、営業時間は10:00〜19:00です」。質問の途中で話題が変わり、聞き直しが増える。

同じ情報を「営業時間：10:00〜19:00、ラストオーダー18:30」「定休日：水曜日」「アクセス：住所」に分ければ、必要なまとまりを選んで読めます。**まず情報を整理し、そのまとまりにHTMLで役目を付けます。** 色を付けるだけでは、話題が混ざったままの文章は整理されません。

### 前回のマークアップ・Markdownとつなげる

マークアップは、文章に「ここは見出し」「ここは段落」などの目印を付けること。HTMLは、そのための**マークアップ言語**です。プログラミングと同じくコードを書いてコンピューターに伝えますが、計算や条件分岐を行うプログラミング言語とは役割が違います。

| 伝えたい役目 | Markdownで書く | HTMLで書く |
|---|---|---|
| 見出し | `## 営業時間` | `<h2>営業時間</h2>` |
| 段落 | `10:00〜19:00`（前後を空行で区切る） | `<p>10:00〜19:00</p>` |

Markdownは、文章の構造を読み書きしやすい記号で示す方法です。HTMLもMarkdownも「見出しや段落として何を伝えるか」を表します。Webページの色・文字の大きさ・余白・並べ方はCSSで表現します。

> [!TIP]
> Markdownなら、**大事なこと**、*補足*、~~やめた案~~、<ins>追記した内容</ins>も短い記号で示せます。[書き方と表示の比較](./markdown-format-guide.md)で、表・チェックリスト・引用・折りたたみも見られます。

**DAY 4の順番：意味を整理する → ワイヤーフレームで順番と配置を考える → HTMLで構造を示す → 見つけやすくなったか確認する。** デザインを変える前に、何の情報かを分かるようにします。DAY 4ではCSSを変えず、構造の改善まで取り組みます。


## このワークブックが学習内容と課題条件の正本です

**目的・依頼・入力データ・作業内容・完成条件・提出するものは、このファイルだけで管理します。** READMEや各回のページは、この正本への入口です。完成条件の一覧も別ファイルへ複製しません。

- **このワークブック：** 学生が何のために、何を変え、何を確認・提出するか。
- **講師用資料：** 時間配分、デモの進め方、支援方法。課題条件はこの正本を参照します。
- **参照資料・配布データ：** Markdownの書式、用語、サンプル、HTML・CSS・画像の実体。課題の条件を独立して追加しません。

標準環境はVS Code＋ローカルファイルです。Git/GitHubを使わずに全15回を進められます。[ZIP提出の手順](../submissions/local-submission.md)に従い、毎回、編集前に作業前ソースを保存し、編集後に作業後ソースを保存します。WORKLOGの8項目、画面、各DAYの証拠をそろえて提出し、講師の指摘を直して再提出します。Git/GitHubを使う場合のPRは[任意の提出経路](../submissions/README.md#任意のprで提出してci判定を受ける)です。

## 毎回のお仕事ルート

1. **メールを開く** — 何を頼まれたのか見つける
2. **作戦を立てる** — 直す場所、直さない場所、質問を決める
3. **技を覚える** — 今日の仕事に必要なHTML・CSSを試す
4. **サイトを直す** — 小さく変更し、ブラウザで見る
5. **チェックする** — パソコン、スマートフォン、キーボードで確かめる
6. **返信する** — 変更したこと、確認したこと、まだ分からないことを伝える

星チェックは振り返りの要点です。完成度だけではなく、質問できたこと、対象外を守れたこと、確認できたことにも星を付けましょう。

### 実習の進め方

### STEP 1　作業場所と依頼を確認する

CodespacesまたはVS Codeで **リポジトリのルート** を開きます。左側に README.md と hht が見えることを確認してください。

次に、教材フォルダーの保存場所が **自分用のコピー** であることを確認します。Gitを使う人だけ自分の作業ブランチを確認します。共有教材のmainを直接編集しません。

依頼から次をメモします。

- Fromはだれか
- Toはだれか
- CCはだれか
- 頼まれていること
- まだ分からないこと
- DAY 1では依頼された文章そのものは変更しないこと

### STEP 2　現在のサイトをローカルで表示する

VS Codeのターミナルを開き、リポジトリのルートで次を実行します。

~~~bash
python -m http.server 8000 --directory hht/starter-site
~~~

#### Codespacesの場合

1. 画面下部の **PORTS** を開く
2. ポート8000を探す
3. **Open in Browser** を押す
4. PORTSに表示された **Forwarded Address** を使う

Forwarded AddressはCodespaceごとに異なります。教材に書かれていないURLを自分で作らないでください。

#### PC上のVS Codeの場合

ブラウザで次を開きます。

~~~text
http://localhost:8000/
~~~

「Address already in use」と出た場合は8001など空いている番号へ変え、ブラウザ側も同じ番号にします。

表示できたら、トップページ、画像、メニューへのリンク、店舗案内へのリンクを確認します。

### STEP 3　開発者ツールで「一時変更」を体験する

[はじめてのブラウザ開発者ツール](./devtools-first-lesson.md)を開き、次を実行します。

1. Elementsでh1を選ぶ
2. h1の文字を一時的に変更する
3. Stylesでcolorまたはfont-sizeを一時的に変更する
4. 再読み込みし、元へ戻ることを確認する
5. 画面幅を375pxにする
6. Consoleに赤いエラーがないか確認する

ここでの変更はHTMLファイルには保存されません。

hht/submissions/day-01/WORKLOG.md の「確認したこと」へ、次のように結果を残します。

~~~text
DevTools: h1確認 / CSS確認 / 375px確認 / Console: エラーなし
~~~

エラーがある場合は「エラーなし」と書かず、最初の1件のメッセージを記録します。

### STEP 4　開始時点を記録し、復元用コピーを作る

#### 標準: Gitなし

[作業前と作業後を保存する](../submissions/local-submission.md#作業前と作業後を保存する)の手順で、現在のstarter-siteとportfolioを教材フォルダーの外へコピーします。作業前フォルダー名を開始バージョンIDとしてWORKLOGへ記録します。模擬公開側の復元用には、エクスプローラーで `hht/practice-server/backups/day-01-<開始ID>` を作り、現在のstarter-site/index.htmlをそこへコピーします。<開始ID>は自分の保存したフォルダー名に置き換えます。

#### 任意: Gitを使う人

別のターミナルを開き、次を実行します。

~~~bash
git status --short
git rev-parse --short HEAD
~~~

2行目に表示された文字列が **開始バージョンID** です。WORKLOG.mdへ記録してください。

次に、表示された開始バージョンIDを使って復元用フォルダーを作ります。以下の <開始ID> を実際のIDへ置き換えます。

~~~bash
mkdir -p hht/practice-server/backups/day-01-<開始ID>
cp hht/starter-site/index.html hht/practice-server/backups/day-01-<開始ID>/index.html
~~~

このコピーは、模擬公開側を戻す練習に使います。

### STEP 5　HTMLを1か所だけ変更する

hht/starter-site/index.html を開き、h1を次のように **DAY 1の練習用** に変更します。

変更前:

~~~html
<h1>一杯から、街の日常をあたためる。</h1>
~~~

変更後:

~~~html
<h1>DAY1練習：一杯から、街の日常をあたためる。</h1>
~~~

保存し、STEP 2で開いたローカルページを再読み込みします。

- 「DAY1練習：」が表示される
- CSSが壊れていない
- メニューと店舗案内へのリンクが動く

ことを確認します。

### STEP 6　変更後のバージョンを残す

#### 標準: Gitなし

保存したstarter-siteとportfolioを、[ZIP提出の作業後フォルダー](../submissions/local-submission.md#作業前と作業後を保存する)へコピーします。作業前のコピーは上書きしません。作業後フォルダー名を変更後バージョンIDとしてWORKLOGへ記録します。

#### 任意: Gitを使う人

変更したHTMLだけをコミットします。

~~~bash
git add hht/starter-site/index.html
git commit -m "DAY1: practice HTML change"
git rev-parse --short HEAD
~~~

最後に表示された文字列が **変更後バージョンID** です。WORKLOG.mdへ記録します。

git commitで「nothing to commit」と出た場合は、index.htmlを保存できているか確認します。Gitの利用自体ができない環境では、[完成条件の「困ったとき」](../student/assignment-checks.md#day-1-環境デプロイ復元)にある日時付きバックアップ方式を使います。

### STEP 7　練習公開する

#### A. 学校から練習用URLと接続方法が配布されている場合

配布された接続票や手順だけを使います。そこに書かれていないホスト名、パス、ユーザー名、パスワードを推測しません。

公開後、実際にブラウザで開いたURLをWORKLOG.mdの「確認URL」へ記録します。

#### B. 練習用URLが配布されていない場合（この教材の標準手順）

practice-server/staging を **模擬公開先** にします。最初だけ、ページ表示に必要なファイルを明示して配置します。

PC上のVS Codeではエクスプローラーでstaging内にcssとimagesフォルダーを作り、index.html、menu.html、about.html、css/style.css、images/hero-cafe.webpを同じ相対位置へコピーすれば、以下のmkdir/cpコマンドは不要です。

~~~bash
mkdir -p hht/practice-server/staging/css hht/practice-server/staging/images
cp hht/starter-site/index.html hht/starter-site/menu.html hht/starter-site/about.html hht/practice-server/staging/
cp hht/starter-site/css/style.css hht/practice-server/staging/css/
cp hht/starter-site/images/hero-cafe.webp hht/practice-server/staging/images/
~~~

フォルダー全体を無条件に上書きせず、何を公開したか分かるようにファイルを指定しています。

次に、別のターミナルで模擬公開先を表示します。

~~~bash
python -m http.server 8001 --directory hht/practice-server/staging
~~~

CodespacesではPORTSの8001から **Open in Browser** を押し、表示されたForwarded Addressを使います。PC上のVS Codeでは http://localhost:8001/ を開きます。

このURLで「DAY1練習：」が表示されることを確認し、WORKLOG.mdには **模擬公開URL** として実際に開いたURLを記録します。

### STEP 8　ソースを開始時点へ戻し、変更後へ戻す

#### 標準: Gitなし

1. STEP 4の作業前コピーからstarter-site/index.htmlだけを、作業中のhht/starter-site/index.htmlへコピーして置き換える。
2. ローカルページを再読み込みし、「DAY1練習：」が消えたことを確認する。
3. STEP 6の作業後コピーから同じindex.htmlだけをコピーして置き換える。
4. 再読み込みし、「DAY1練習：」が戻ったことを確認する。

作業前・作業後の保存フォルダー自体は編集しません。復元結果と画面を提出記録に残します。

#### 任意: Gitを使う人

STEP 4で記録した開始バージョンIDを使います。<開始ID> を実際のIDへ置き換えてください。

~~~bash
git restore --source=<開始ID> -- hht/starter-site/index.html
~~~

ローカルページを再読み込みし、「DAY1練習：」が消えたことを確認します。

確認できたら、変更後コミットの内容へ戻します。

~~~bash
git restore --source=HEAD -- hht/starter-site/index.html
~~~

再読み込みし、「DAY1練習：」が再び表示されたことを確認します。

これで **変更前へ戻せる / 変更後へ戻せる** ことを確認できました。

### STEP 9　模擬公開先も一度戻す

STEP 7でBの模擬公開を使った人だけ行います。PC上のVS Codeではエクスプローラーで、バックアップのindex.htmlをstaging/index.htmlへコピーして置き換え、確認後に作業中のstarter-site/index.htmlで置き換え直します。以下は同じ操作のコマンド例です。

<開始ID> を実際の開始バージョンIDへ置き換えます。

~~~bash
cp hht/practice-server/backups/day-01-<開始ID>/index.html hht/practice-server/staging/index.html
~~~

模擬公開URLを再読み込みし、「DAY1練習：」が消えたことを確認します。

次に、現在の変更後HTMLをもう一度配置します。

~~~bash
cp hht/starter-site/index.html hht/practice-server/staging/index.html
~~~

再読み込みし、「DAY1練習：」が戻ったことを確認します。

この **戻した画面 / もう一度反映した画面** を復元記録として残します。

### STEP 10　WORKLOGと受領返信を完成させる

[提出フォルダーの使い方](../submissions/README.md)に従い、hht/submissions/day-01/WORKLOG.md を作ります。Gitなしの人は[ZIP提出](../submissions/local-submission.md)で提出します。質問や未確認がないときは「なし（理由）」と書き、空欄や例のままにしません。

最低限、次を埋めます。

~~~md
DAY 1 作業記録
- 依頼: 「創業10年」の文章修正依頼を受領。DAY 1では環境確認と復元練習まで実施
- 質問:
~~~

```html
<section>
  <h2>アクセス</h2>
  <p>北海道札幌市北区北00条西0丁目（架空）</p>
</section>
```

同じ話題の見出しと本文がまとまるよう、元の内容を移します。タグを変えるときは、開始タグと終了タグを組で確認します。見出しの大きさではなく、**ページの題名→各話題**の関係で `h1`・`h2` を選びます。

**判断メモ：** 「＿＿を先にした。＿＿を1つのまとまりにした。見る人が＿＿を探すため。」

#### sectionとdiv：見た目は同じにできる。役目は違う

**`section`（セクション）と`div`（ディビジョン）は、今回のようなまとまりでは置き換え可能です。ただし、意味まで同じになるわけではありません。**

| 選ぶタグ | 伝える役目 | 選ぶ場面 |
|---|---|---|
| `section` | 1つの話題のまとまり | 「営業時間」「アクセス」など、見出しを付けて説明する部分 |
| `div` | 特定の意味を持たないまとまり | CSSで横並びにする、背景を付けるなどのためにまとめる部分 |

**HTMLは内容の役目を伝え、CSSは色・余白・配置などのデザインを決めます。** `section`は「四角く囲む」「横に並べる」というデザインの指定ではありません。同じCSSを使えば、`div`でも同じ見た目にできます。

![同じinfo-cardクラスを付けたsectionとdivをChromeで表示した比較。どちらも同じ枠・色・余白だが、sectionは話題のまとまり、divは意味を持たないまとまり](../assets/day34/day4-tag-comparison.png)

[この比較ページを開く](../lessons/04/tag-comparison.html)。上の2つの枠は同じ `.info-card` を使用。下の例はタグ名を指定したCSSがあるため、タグを替えると見た目も変わります。

```html
<!-- 話題としてまとめる -->
<section class="info-card">
  <h2>営業時間</h2>
  <p>10:00〜19:00</p>
</section>

<!-- 特定の役目を付けずにまとめる -->
<div class="info-card">
  <h2>営業時間</h2>
  <p>10:00〜19:00</p>
</div>
```

**置き換えるときの確認：**

- 開始タグと終了タグを両方替える。本文、class、id、リンク先は理由なく変更しない。
- CSSに `section { ... }` や `main > section` があると、`div`へ替えた部分にそのCSSは当たらなくなる。同じ見た目を保つには、必要な指定を共通classで受けられるか確認する。
- JavaScriptにもタグ名を指定した処理があれば、対象が変わる。今回の店舗案内にはその処理はない。
- 見出しと本文の関係、ブラウザや読み上げソフトに伝わる役目を確認する。`main`・`nav`や名前付きの`section`を`div`に替えると、役目が自動で同じように伝わるわけではない。
- どこにでも置けるわけではない。たとえば `p`の中に`section`や`div`は入れない。置く場所と中身の条件を確認する。

**「デザインを指定するタグではない」と「替えても必ず見た目が同じ」は別です。** ブラウザには最初から用意されたCSSもあり、タグによって初期の見た目が違う場合があります。保存後に再読み込みし、表示も確認します。

#### ほかにも、同じ見た目にできるタグはある？

次は**見た目を同じにできても、意味は等価ではない**例です。タグは色や形でなく、内容の役目で選びます。この表は必要なときに読むヒントです。今、全種類を覚える必要はありません。

| 比較するタグ | 意味の違い・置き換えの注意 |
|---|---|
| `article` と `div` | `article`は単独でも成り立つ記事など。`div`にするとその役目がなくなる |
| `nav`・`main` と `div` | ページ移動・中心内容という役目がある。`div`で同じ配置を作れても、役目は同じにならない。今回の`main`を消さない |
| `strong` と `b` | 初期表示はどちらも太字になりやすい。`strong`は重要性、`b`は重要性を加えず注意を引く部分。太くするだけならCSS |
| `em` と `i` | 初期表示はどちらも斜体になりやすい。`em`は強調、`i`は専門用語や別の声・調子など。斜めにするだけならCSS |
| `time` と `span` | 同じ文字を表示できる。`time`は日付・時刻を表し、`datetime`で機械にも値を伝えられる。`span`にはその意味や専用属性がない |

`a`と`button`は同じ形にできても、リンク移動と操作という機能が違います。`h2`と`div`も、同じ文字サイズにできても見出しとしての役目が違います。**見た目が似ているからといって、どのタグでも自由に交換できるわけではありません。**
