# 全日程の共通手順と作業メモ

[目次へ戻る](../student-workbook.md)

**目的：** 教材を更新しながら、自分の成果を失わずに残します。  
**見る人：** 制作する自分と講師です。  
**ゴール：** 教材と成果の保存先を区別し、変更・確認結果をPRで渡せるようにします。

<a id="local-git-workflow"></a>

Gitは全15回で使います。  
教材eduでは開始時の差分確認・変更の保護・破棄・Pullを行います。  
DAY10以降の作品は、教材とは別のGit管理で保存・コミットします。  
全DAYの提出は[PR提出方針](#submission-policy)に従います。

<a id="clone-edu"></a>

## 初回だけ：Documentsへ教材をクローンする

GitHubの[教材リポジトリ`hgsk/edu`](https://github.com/hgsk/edu)を、自分のPCのDocumentsへ取得します。  
**クローン**は、ファイルとGitの履歴をまとめてPCへコピーする操作です。  
GitとVS CodeがインストールされたPCで進めます。

1. VS Codeを開き、`Ctrl + Shift + P`を押します。
2. `Git: クローン`を選び、次のURLを入力してEnterキーを押します。

```text
https://github.com/hgsk/edu.git
```

![VS Codeのクローン操作でhttps://github.com/hgsk/edu.gitを入力した実画面](../../assets/vscode/02-clone-url.jpg)

**見るところ：** 入力欄のURLが`https://github.com/hgsk/edu.git`になっていることを確認します。

3. 保存先を選ぶ画面で、左側の「ドキュメント」を開き、「リポジトリの宛先として選択」を押します。
4. クローンが終わったら、「開く」を押します。
5. VS Codeのエクスプローラーで、`edu`の中に`README.md`と`hht`があることを確認します。

Documentsは、Windowsで「ドキュメント」と表示されるフォルダーです。  
OneDriveを利用しているPCでは、OneDrive内の「ドキュメント」になることもあります。  
この中に`edu`が作られ、作業場所は`Documents/edu`になります。

既に`edu`があるときは、削除や上書きをせず、そのフォルダーを開いて講師と確認します。  
クローン後はGitの履歴があるので、`git init`や初期コミットは行いません。

<a id="windows-safe-update"></a>

## Windowsで以前クローンした教材を更新するとき

**依頼：** 講師から新しい教材を受け取る際に、自分の制作途中のファイルと履歴を守ります。  
**対象：** 改行変換を止める設定（`.gitattributes`）が入る前に取得したWindowsの教材です。  
**完成条件：** 元のフォルダーを残したまま、新しい教材で検証が成功し、移した自分の変更を説明できます。

### 1. 元の作業を保存して確認する

VS Codeの「ファイル → すべて保存」を選びます。  
元の`edu`で、次の読み取り専用コマンドを実行します。

```powershell
git status --short --untracked-files=all
git log -1 --oneline
```

変更一覧と最後のコミットを講師に見せます。  
一覧が空でも、自分のコミットや無視されているファイルは存在することがあります。  
一覧だけを根拠にフォルダーを削除しません。

### 2. 元を残し、別の場所に新しい教材を取得する

教材を開いているサーバーや実行中の処理を停止してから、エクスプローラーで元の`edu`フォルダー全体を別の場所へコピーします。  
隠しフォルダー`.git`、未追跡の画像、作業メモも含め、コピー先のファイルが開けることを確認します。  
コピーに失敗した場合はここで止めて講師に相談します。  
元の`edu`もそのまま残します。

エクスプローラーで新しい親フォルダーを作り、空であることを確認します。  

![WindowsのエクスプローラーでDocuments内のedu-update-20261029を開き、空の保存先を確認した実画面](../../assets/windows-update/01-separate-destination.png)

**見るところ：** アドレス欄が元の`Documents/edu`と別の場所で、中央に空のフォルダーと表示されています。  
この新しい親フォルダーを保存先にします。

[初回のクローン手順](#clone-edu)を使い、新しく作った空の親フォルダー（例：`Documents/edu-update-20261029`）を保存先に選びます。  
新しい教材は、その中の`edu`へ取得されます。  
既存の`Documents/edu`やバックアップ先へ上書きしないでください。

![VS CodeのクローンURL入力画面。新しい教材も同じURLから別の親フォルダーへ取得する](../../assets/vscode/02-clone-url.jpg)

**見るところ：** URLは同じでも保存先は別です。  
VS Codeで新しい`edu`を開き、ウィンドウのタイトルと「ファイル → フォルダーを開く」の場所を確認します。

![VS Codeで別の親フォルダー内の新しいeduを開き、タイトルに作業場所が表示されたWindowsの実画面](../../assets/windows-update/02-new-working-folder.png)

**見るところ：** `edu-update-20261029`内の`edu`を開いています。  
初回の案内画面が出る場合は、サインインせずに続けるか案内を閉じて、作業フォルダーを確認します。

### 3. 新しい教材を検証してから、自分の変更を移す

新しい`edu`のターミナルで、講師と次を確認します。  
検証にはPythonとPillowが必要です。  
見つからない場合は教材ファイルを直さず、講師に環境の準備を依頼します。

```powershell
git check-attr text -- hht/day01/index.html
python hht/scripts/validate-course.py
python unity/scripts/build_course.py --check
python -m unittest discover -s unity/scripts -p "test_*.py"
python -m unittest discover -s hht/scripts -p "test_*.py"
```

属性の表示が`text: unset`となり、教材検証がPASS、単体テストがOKになることを確認します。  
設定を取り込むだけでは、元の作業コピーで既に変換された改行は自動修復されません。

![新しい作業場所、text unset、教材検証PASS、単体テストOKをVS Codeで確認したWindowsの実画面](../../assets/windows-update/03-validation-results.png)

**見るところ：** 画面例はWindows CIで実行した上記コマンドの結果を、確認用テキストとして開いたものです。  
`Working folder`が新しい保存先で、`text: unset`、`PASS`、`OK`、終了コード0が並んでいます。  
自分のPCではターミナルの結果を読み、同じ成功表示を確認します。  
テスト件数は教材の更新により増えることがあります。

検証に成功したら、講師と元の作業の差分を読み、自分が編集したDAYのファイル・追加画像・作業メモだけを新しい教材へ移します。  
元のフォルダー全体や`.git`、教材のZIP、撮影記録、Unityのビルドをまとめて上書きしません。  
自分のコミットやタグを引き継ぐ必要がある場合は、講師と移行方法を決めるまで元のフォルダーで作業を続けます。

移した後はブラウザーで制作物を確認し、VS Codeのソース管理で自分の変更だけがあることを確認します。  
改行だけの大量の差分が出た場合は、コミットせず講師に見せます。  
必要な変更をコミットし、次回開く新しいフォルダーの場所を作業メモへ残します。  
元のフォルダーとバックアップは、作業と履歴の移行を講師と確認し終えるまで残します。

**使わない操作：** この更新で`git reset --hard`、`git clean -fd`、`git rm --cached -r .`や変更の一括破棄は行いません。  
`git stash`だけをバックアップの代わりにせず、未追跡・無視対象のファイルもフォルダー全体で保護します。

**改行の保存：** 新しく作るテキストは原則LFで保存します。  
既存ファイルのLF・CRLFは維持し、教材全体の一括変換はしません。

<a id="independent-day-start"></a>

## 毎回の開始：教材を確認し、更新する

古いWindowsの教材は、先に[安全な更新手順](#windows-safe-update)を確認します。  

1. VS Codeで`Documents/edu`を開き、フォルダー名とソース管理のリポジトリを確認します。
2. 変更一覧のファイルを開き、差分を読みます。
3. 残したい練習結果・画像・作業メモは、**破棄前に教材の外へコピー**します。  
   コピー先を開き、必要なファイルが読めることを確かめます。  
   作品がedu内にある場合も、先に保護して講師へ相談します。
4. 元へ戻してよいと確認した追跡済みファイルだけ、ソース管理の「変更の破棄」を行います。  
   破棄すると、その未コミット変更は戻せなくなる可能性があります。
5. 未追跡ファイルは新しく作った成果かもしれません。  
   一括削除せず、中身を確認して保護します。
6. 変更一覧を再確認してから、登録済みの取得先・ブランチに対して「Pull」を行います。
7. エラーがないことと教材の更新結果を確認し、今日のDAY本文を開きます。

ここでの「チェックアウト（帳消し）」は、練習変更を戻す操作です。  
ブランチ切替とは区別します。  
Pullは教材の更新を取り込む操作で、自分の作品のバックアップではありません。  
競合・認証・取得先不明で止まったら、画面を講師へ見せます。  
強制リセット、全削除、取得先やブランチの独断での切替は行いません。

**実画面の整備状況：** 差分確認は下の既存画像で参照できます。  
変更の破棄・Pullと、教材外の作品を開き分ける新運用の実画面は未収録です。  
講師が学校PCで操作を確認し、撮影・掲載するまで、この部分の画面教材は未完了です。

![VS Codeのソース管理で文章の変更前後を比べた既存の実画面](../../assets/workbook/common/02-diff-clean.jpg)

**見るところ：** 左が変更前、右が変更後です。  
画像の10年→11年は差分操作の例で、DAY2の変更先はDAY2本文を確認します。  
この画像は変更の破棄やPullの操作証拠ではありません。

### DAY1〜9：基礎練習を開く

DAY1〜9は、他のDAYを終えていなくても始められます。  
クローンした`edu`の`hht/day01`〜`hht/day09`から、その日の本文で指定されたファイルを編集します。  
前回の成果は教材更新前に保護し、その日の練習は配布状態から始めます。

![VS CodeでeduとDAY06のHTML・CSSを開いた既存の実画面](../../assets/direct-days/day-folders.png)

**見るところ：** 左のエクスプローラーと上のパンくずでDAYとファイル名を照合します。  
旧DAY10〜15のフォルダーも残っていますが、現行後半授業の作業先ではありません。

<a id="portfolio-start"></a>

## DAY10の初回準備：教材の外に作品を置く

**準備するもの：** 教材とは別の`Documents/portfolio`です。  
同名のフォルダーが既にあれば、上書きせず講師と確認します。

1. `Documents`に`portfolio`フォルダーを作ります。  
   eduの中に作りません。
2. 簡単な白紙ひな型として、教材の`hht/day14/index.html`と`css`フォルダーをportfolioへコピーできます。  
   旧DAY14という名前のままのコメントは、記入位置の目印として利用します。  
   Gitの管理情報`.git`はコピーしません。
3. VS Codeの「ファイル → フォルダーを開く」で、そのportfolioを開きます。
4. フォルダーの場所を確認してから、ソース管理の「リポジトリを初期化」で、この作品だけをGit管理します。  
   既に履歴がある作品は初期化し直しません。
5. `index.html`をブラウザで開きます。  
   白紙ひな型は本文がコメントだけなので、最初は白いページです。
6. DAY10本文の紹介と作品・作業内容を書きます。  
   作品へのリンクが必要なら、保護した本人の成果を`portfolio/works/`などへコピーします。  
   HTMLだけでなく、参照しているCSS・画像もそろえます。
7. `../edu/hht/dayNN/…`へのリンクは使いません。  
   教材の更新に影響されない、portfolio内の実際の保存先への相対リンクにします。

`hht/day14/reference-cafe`は架空の参考作品です。  
教材の作品全体を、自分が制作した実績として掲載しません。  
欠席者も白紙ひな型と実際にした作業の説明から始められます。

**画面教材：** この準備に必要なフォルダーコピー・Git初期化の新しい実画面は未収録です。  
教材が揃ったと扱わず、学校PCでの撮影と確認を残課題にします。

## DAY10〜15：同じ作品を記録して続ける

毎回、教材eduの更新を終えたら、同じportfolioへ切り替えます。  
作品では変更を破棄しません。

1. 小さく編集し、Ctrl+Sで保存します。
2. ブラウザで再読み込みし、文章・表示・必要なリンクを確かめます。
3. ソース管理で差分を読み、不要な変更や個人情報がないか確認します。
4. 記録したいファイルの「＋」でステージします。
5. 「作品紹介の説明とリンクを追加」など、何を変えたか分かるメッセージでコミットします。
6. コミット結果と残った変更を確認し、次に直す所をメモします。

コミットはローカル履歴への記録です。  
PushやPR作成は別の操作です。  
新運用では教材の毎回コミットと`dayNN-end`タグを必須にしません。

<a id="submission-policy"></a>

## 全DAYの提出：GitHub PR

全15回ともGitHub PRで提出します。  
提出用ZIPの作成・圧縮・USB回収は行いません。  
開始データの配布ZIPは提出用ではなく、通常はクローンした教材を使います。

**提出先を先に確認します。**  
講師が指定した本人用リポジトリ、PRのbaseブランチ、講師の閲覧権限を確認します。  
教材`hgsk/edu`へ学生作品を送る運用とは決めていません。  
提出先が未案内なら、ローカル成果を保護したまま講師へ確認し、PR提出済みとは扱いません。  
新スライドは提出先とブランチ方式を指定していないため、学校側の設定確定が必要です。

- **DAY1〜9：** 練習で変更した制作ファイル、使うCSS・画像、表示・操作の確認結果、[WORKLOGと証拠](../../submissions/README.md)を教材外に保護します。  
  確認した本人用提出先の作業ブランチへ記録してPushし、指定baseへのPRを作ります。  
  教材eduには学生成果のコミットを残すことを求めません。
- **DAY10〜15：** 同じportfolioの変更と作業メモを作品側のGitへコミットします。  
  指定された作品側の作業ブランチをPushし、指定baseへのPRでその回の変更を示します。  
  次回のブランチの作り方は、講師のマージ・返却方式に合わせて確認します。

PR本文には、DAY、目的、変更箇所、実際に確認した結果、残件、対象コミットSHAを書きます。  
必要なスクリーンショットには対象箇所の説明を添えます。  
PRを開き、Files changedで本人の対象ファイルが入り、別DAYや認証情報が混ざっていないか確認します。  
PRのURLを講師指定の窓口へ渡します。  
PR提出はWebサイトの外部公開とは別です。  
相互レビューを授業の完成条件にすることとも別です。

**CIの境界：** この教材のQuality CIは教材構造・リンク・開始データを確認します。  
学生作品の完成や合格を自動判定しません。  
[Student Assignment](../../submissions/README.md#ci-checks)は提出物の形式と証拠の有無を確認します。  
旧課題の採点条件や点数・合否は自動適用しません。  
講師は完成条件・画面・差分を確認し、同じPRへ修正依頼を返します。  
提出先側のCI設定が未完了なら、未検証と記録します。

<a id="work-notes"></a>

## 毎回使う作業メモ

```markdown
# DAY 作業メモ

- 見る相手・目的：
- 直す場所／直さない場所：
- 変更したこと：
- 実際に確認したこと・結果：
- 未確認・次にすること：
- 保存先・コミットSHA：
- 提出PR URL（作成後）：
```

必要な成果の保護と、表示・リンクの確認を終えてから教材を更新します。
