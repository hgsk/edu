# Git・LAN／P2P共有でワンタッチ提出

GitHubアカウント、PR、インターネット接続は不要です。Gitで作業前・提出版を記録し、自己完結した`git bundle`と提出記録JSONを共有フォルダーへ転送します。DAY 01〜15で同じ操作を使います。手作業でZIPを作る代わりに選べる提出経路です。完成条件、WORKLOGの8項目、画面・証拠、講師レビュー、評価基準は共通です。

## 初回設定

1. **GitとNode.js（22以降）**を使えるPCを用意します。追加のnpmパッケージやPythonは不要です。インストール後はVS Codeを再起動します。
2. VS Codeで自分用教材のルート（README.mdとhhtが見える位置）を開きます。Git cloneで取得した教材でも、ZIP展開した教材でも使えます。教材原本のGitブランチ・ステージ済みファイルには触れません。
3. 講師は匿名の提出番号（例：`s001`）と、既存の提出先フォルダーを配布します。初回はコマンドパレットの「Tasks: Run Task」から**HHT: 提出先を設定**を選び、この2つを入力します。
4. 学校管理の提出先は、学生ごとの書き込み権限と他の学生の提出を読めない権限を用意します。受領物は講師の別領域へ保管します。提出番号は自己申告なので、本人確認は学校の配布・受領記録で行います。

提出先に使える例（実際の接続先は講師から配布）：

| 共有手段 | 指定する場所 | 接続条件 |
|---|---|---|
| 同じLANのSMB共有 | `\\講師PC\提出`、ネットワークドライブ | 学校が共有設定・アクセス権を準備。認証はOS側で行う |
| P2P同期 | 端末間で同期する既存フォルダー | 同期ソフトの接続・共有範囲は事前設定。講師側にJSONとbundleが両方届くまで待つ |
| USB／直接受け渡し | 教材の外にあるUSB上のフォルダー | 相手PCにネットワーク接続は不要 |
| 検証用のローカル共有 | 教材の外にある別フォルダー | 転送の動作確認用。講師受領には別途受け渡しが必要 |

設定と履歴は教材ルートの`.hht-submit/`に保存され、教材リポジトリのGit管理から除外されます。共有先の認証情報を入力・保存する機能はありません。

## 毎回の操作

1. **編集前**に「Tasks: Run Task」→ **HHT: 作業開始を記録**で今日のDAYを選びます。表示された実際の開始コミットIDをWORKLOGのバージョン欄へ記録します。同じDAYで再実行しても開始時点は上書きしません。
2. 今日の課題を制作・確認します。`hht/submissions/day-NN/WORKLOG.md`の8項目、`screenshots/`の画像、`evidence/`の確認記録を保存します。未実施はNOT RUN、進められない項目はBLOCKEDと記録し、確認を捏造しません。
3. **Ctrl+Shift+B**（Macは**Cmd+Shift+B**）を押すと既定タスク **HHT: 提出**が実行されます。変更ファイルはタスク実行前に保存され、提出用Gitへコミット、bundle作成、共有先転送まで進みます。コマンドパレットから同タスクを選んでも実行できます。
4. ターミナルの「転送完了」、提出JSON名、開始・変更後のIDを確認します。変更後の正確なIDは提出JSONの`head`に記録されます。WORKLOGでは「変更後=提出JSONのhead参照」と書けます。コミット自身のIDをそのコミット内のWORKLOGに埋め込む必要はありません。
5. 講師が受け取り検証して受領を返すまで、提出完了と判断しません。P2P同期では、学生側の「転送完了」はローカル同期フォルダーへの保存完了です。講師側への到達を意味しません。

開始記録を忘れた場合、後から記録した状態を編集前と称しません。WORKLOGにBLOCKED（開始記録なし）と記載して講師へ相談し、既存の保存コピー／ZIP提出で補います。提出タスクは開始記録なしでは停止します。

## 送る内容と履歴

- `hht/starter-site/`、`hht/portfolio/`のソース・CSS・画像
- `hht/practice-server/staging/`、`production/`、`backups/`に実際に保存した公開・復元用ファイル
- 今日の`hht/submissions/day-NN/`のWORKLOG、画像、証拠
- 上記だけで構成した提出専用Gitの履歴。教材本体の`.git`、教材一式、講師用回答、接続票はコピーしません。過去の自分の提出履歴はbundleに含まれます。

提出時にファイル数や完成条件の合否を自動採点する機能ではありません。WORKLOGの基本記入・証拠の存在を確認し、明らかな秘密情報、秘密鍵用ファイル、リンク、20MB超の単一ファイルは拒否します。秘密情報の検出は完全ではないため、提出対象には認証情報を保存しません。提出先は教材フォルダーの外に置きます。

ファイル名は`提出番号-day-NN-r版-一意ID.bundle`と同名の`.json`です。JSONはbundle転送・チェックサム検証後に作る完了マーカーです。同名の別内容を上書きしません。提出専用履歴へのコミットは授業の合格や公開承認を意味しません。

## 失敗・再提出

- LAN切断／同期先不在でも、コミットと提出物は`.hht-submit/outbox/`に残ります。接続を直して **HHT: 前回の提出を再送**を実行すると、同じ版を再送できます。
- 転送途中で中断し不完全な同名bundleが残った場合、再送は上書きせず停止します。講師に相談し、完成JSONのない不完全な転送ファイルだけを提出先から除去して再送します。正常に受領した版は削除しません。
- 指摘を直し、WORKLOGと証拠を更新して **HHT: 提出**を再実行するとr2、r3と増えます。元の開始時点と以前の提出物は保持します。
- `.hht-submit/`には開始時点と未転送の提出物があるため削除しません。PCを移す際は、教材と一緒にバックアップします。

## 講師の受け取り・レビュー

講師PCでは、自分が管理する教材リポジトリ内のコマンドを実行します。学生が送ったスクリプトは使いません。提出JSONとbundleを同じフォルダーにそろえます。

```sh
node hht/scripts/submit.mjs receive --manifest "/共有/s001/提出名.json" --output "/レビュー/s001-day01-r1"
```

Windowsでは配布されたUNCパス、ネットワークドライブ、ローカル保存先を引用符で囲みます。outputは既存でない新しいフォルダーにします。

受け取りコマンドはチェックサム、Git bundle、提出コミットと開始コミットのつながり、対象パス、リンク／submoduleの不在を検証します。学生コードやGit hookは実行しません。検証成功時に次を保存します。

| 受け取り先 | 確認する内容 |
|---|---|
| `hht/` | 提出版のソース・画面・証拠 |
| `REVIEW.diff` | 記録された開始時点と提出時点の差分 |
| `RECEIPT.json` | 受領日時、提出番号・DAY・版、開始／提出コミットID |
| `.git/` | 提出専用履歴。`git show 開始ID:相対パス`で開始ファイルを確認可能 |

開始時点は学生が記録したものなので、初回配布物／前回受領版とも照合します。チェックサムは破損検出であり本人証明ではありません。受領確認・指摘は学校の非公開返却経路で返します。[完成条件](../student/assignment-checks.md)を同じ順序で確認し、見た目、Tab操作、公開・復元、承認の根拠もレビューします。CI欄は`NOT RUN（Git bundle提出、GitHub Actions未実行）`とし、成績は[ルーブリック](../docs/rubric.md)に従います。

## ターミナルでの同じ操作

```sh
node hht/scripts/submit.mjs setup --student s001 --destination "/共有/提出"
node hht/scripts/submit.mjs begin --day 01
node hht/scripts/submit.mjs submit
node hht/scripts/submit.mjs send
```

この仕組みはファイル共有を利用します。P2Pピア発見、SMBサーバーの起動、ファイアウォール変更、GitHubへのpush、教材mainへのmergeは行いません。
