# 第14章 VRAMとHBM


[目次](../README.md) · [前の章：第13章 データベース](./lesson13.md) · [次の章：第15章 ML推論と学習](./lesson15.md)


**この章で学ぶこと：** GPUのメモリ階層を、コアレッシング、共有メモリ、レジスタ圧とオキュパンシー、ホスト間転送の観点で設計できるようになります。


GPUは、メモリの壁が最も先鋭化した環境です。  
演算器の数に対して帯域が細く、アクセスの形がそのまま性能になります。  
CPUの階層で学んだ原理が、より露骨な形で現れます。


## 考え方


- **コアレッシング：**
  隣り合うスレッドが隣り合うアドレスを読むと、転送をまとめられます。  
  ストライドのあるアクセスは、運んだバイトの大半を捨てます。  
  AoSとSoAの議論が、そのままカーネルの設計になります。


- **共有メモリは手動のキャッシュ：**
  オンチップの共有メモリは、プログラマが明示的に出し入れするキャッシュです。  
  タイリングと組み合わせ、再利用するブロックを載せます。  
  バンクコンフリクトという、この階層特有の競合もあります。


- **レジスタ圧とオキュパンシー：**
  1スレッドあたりのレジスタと共有メモリの使用量が、同時実行できるスレッド数を決めます。  
  保持を増やすと、並列で隠せるレイテンシが減ります。  
  第4章のレジスタの議論が、ここで規模を変えて再登場します。


- **ホスト間転送：**
  CPUとGPUの間の転送は、PCIeやNVLinkという細い橋を渡ります。  
  ピン留めメモリや非同期転送で効率と重ね合わせを改善できます。  
  小さな転送の頻発は、固定費の繰り返しで不利になります。


## ハンズオン：アクセスパターンを変えてカーネルを測る


1. 配列を処理する単純なカーネルを用意し、実行時間を測ります。
2. スレッドとデータの対応を変え、ストライドアクセスにして再測定します。
3. ブロック単位で共有メモリへ載せる版を作り、再利用の効果を測ります。
4. ホスト間転送の時間を分けて測り、全体に占める割合を確認します。


GPU環境がない場合は、公開されている測定結果と自分の見積もりを照合する形でも構いません。  
その場合は、見積もりの根拠を明記してください。


## 代償と判断


共有メモリの使用量を増やすと、同時に走るブロック数が減ります。  
転送と計算の重ね合わせは、コードとバッファ管理を複雑にします。  
最適なタイルサイズは、ハードウェア世代ごとに変わります。


## 確認


- [ ] コアレッシングが崩れる条件を説明できる

- [ ] 保持とオキュパンシーの交換を説明できる

- [ ] 転送コストを全体の会計に入れられる


**演習：** 自分の知っているGPU処理を1つ選び、運搬の観点で律速箇所を予測してください。  
予測を確かめる測定方法も書いてください。
