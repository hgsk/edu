# 第16章 運ぶバイトを減らす


[目次](../README.md) · [前の章：第15章 ML推論と学習](./lesson15.md) · [次の章：第17章 分散キャッシュ](./lesson17.md)


**この章で学ぶこと：** シリアライゼーションと圧縮の選択を、サイズ、変換コスト、読みやすさの会計で判断できるようになります。


ネットワークの章に入ります。  
ここからは、運ぶこと自体に時間とお金がかかります。  
最も確実な最適化は、運ぶバイトそのものを減らすことです。


## 考え方


- **フォーマットの会計：**
  テキスト形式は読みやすい反面、数値やキーの繰り返しでサイズが膨らみます。  
  バイナリ形式は小さく変換も速い一方、スキーマ管理が必要です。  
  列指向形式は、必要な列だけを読むことで運搬を減らします。


- **圧縮の選択：**
  圧縮は、帯域と容量をCPUで買う交換です。  
  速いコーデックと高圧縮コーデックでは、釣り合う回線速度が異なります。  
  すでに圧縮されたデータの再圧縮は、ほぼ無駄です。


- **ペイロード設計：**
  不要なフィールドの送信、過剰な精度、重複した表現は、静かな浪費です。  
  ページングと部分取得は、運搬の単位を需要に合わせる設計です。  
  APIの設計が、そのまま運搬コストの設計になります。


## ハンズオン：同じデータを3形式で比べる


1. 実務に近いデータ集合を用意し、テキスト形式で保存してサイズを測ります。
2. バイナリ形式と、圧縮をかけた形式でもサイズを測ります。
3. それぞれの書き込みと読み込みの時間も測ります。
4. 結果を、回線速度の異なる2つの前提で評価します。


最速の形式は前提で変わります。  
前提を明記して結論を出すことが目的です。


## 代償と判断


圧縮は、レイテンシの小さい対話的な通信では逆効果になることがあります。  
バイナリ形式は、デバッグのしやすさと引き換えです。  
ペイロードの削減は、将来の利用側の柔軟性を狭めることがあります。


## 確認


- [ ] フォーマットの得失をサイズと変換コストで説明できる

- [ ] 圧縮が釣り合う条件を回線速度で説明できる

- [ ] ペイロード設計が運搬コストになる例を挙げられる


**演習：** 自分の関わるAPIやファイル形式を1つ選び、運んでいるのに使われていないフィールドがないか点検してください。
