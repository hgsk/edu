# 第17章 分散キャッシュ


[目次](../README.md) · [前の章：第16章 運ぶバイトを減らす](./lesson16.md) · [次の章：第18章 プールと配置の分散版](./lesson18.md)


**この章で学ぶこと：** TTLと無効化、キャッシュスタンピード、ホットキーを理解し、分散キャッシュの採否と設計を価値密度で判断できるようになります。


分散キャッシュは、メモリ階層をネットワークの向こうへ延長したものです。  
原理はCPUキャッシュと同じですが、失敗の仕方が分散特有のものになります。


## 考え方


- **TTLと無効化：**
  分散したコピーの鮮度を保つ方法は、時間で切るか、変更を通知するかです。  
  TTLは単純ですが、古い値を返す窓ができます。  
  明示的な無効化は正確ですが、通知の仕組み自体が複雑さを持ち込みます。


- **キャッシュスタンピード：**
  人気のあるキーが一斉に切れると、要求が一斉に源泉へ殺到します。  
  対策は、再計算の直列化、先行更新、期限のばらつきです。  
  キャッシュは、源泉を守るためにあるのに、切り替えの瞬間に源泉を倒すことがあります。


- **ホットキーと複製：**
  アクセスが集中するキーは、1つのノードの帯域とCPUを律速にします。  
  複製と分割は、集中を分散させる手段です。  
  これはNUMAでの共有データの複製と同じ判断です。


- **HTTPとブラウザのキャッシュ：**
  分散キャッシュと同じ原理が、ブラウザとプロキシにも働いています。  
  Cache-Controlの設計は、TTLと無効化の設計そのものです。  
  第20章のCDNは、この延長にあります。


## ハンズオン：キャッシュの有無と一斉失効を観察する


1. 読み取りの多い処理を用意し、キャッシュなしでの源泉への要求数を数えます。
2. キャッシュを入れ、ヒット率と源泉の負荷の変化を記録します。
3. 有効期限を一斉に切れる設定にし、同時要求で源泉への集中を観察します。
4. 期限のばらつきなどの対策を入れ、再測定します。


小規模な再現で構いません。  
集中の形を一度見ることが目的です。


## 代償と判断


キャッシュの導入は、鮮度の問題と運用対象を増やします。  
ヒット率を追うあまり大きなものを何でも入れると、価値密度の低い保持が増えます。  
源泉が十分に速い場合、キャッシュは複雑さだけが残ります。


## 確認


- [ ] TTLと明示的無効化の得失を説明できる

- [ ] スタンピードの発生条件と対策を説明できる

- [ ] ホットキーの対策を、他の階層の原理と結び付けられる


**演習：** 自分のシステムでキャッシュされているものを1つ選び、失効の方式とスタンピード耐性を点検してください。
