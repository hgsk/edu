# 第20章 CDN


[目次](../README.md) · [前の章：第19章 フロントエンド](./lesson19.md) · [次の章：第21章 エッジコンピューティングとデータグラビティ](./lesson21.md)


**この章で学ぶこと：** CDNを地球規模のキャッシュとして設計し、ヒット率、キャッシュキー、失効、stale-while-revalidateを使い分けられるようになります。


CDNのエッジは、ユーザに最も近いキャッシュです。  
ここまで学んだキャッシュの原理が、惑星規模でそのまま働きます。  
失敗の形も、キーの設計と失効に集約されます。


## 考え方


- **ヒット率の支配：**
  エッジでヒットすれば、オリジンへの往復と帯域が丸ごと消えます。  
  ヒット率は、対象の選定とキーの設計で決まります。  
  オリジンの負荷と費用は、ヒット率の関数です。


- **キャッシュキーの設計：**
  キーに含める要素が増えるほど、別物として保持され、ヒット率は下がります。  
  Varyの指定ミスは、ヒット率の低下と、誤った応答の共有の両方を招きます。  
  クエリパラメータやCookieの扱いが、典型的な論点です。


- **失効とpurge：**
  世界中に散ったコピーを消す操作には、時間と費用がかかります。  
  バージョン付きURLは、消すのではなく新しい名前で置く設計です。  
  失効の設計は、コンテンツの更新頻度とセットで決めます。


- **stale-while-revalidate：**
  古い応答を返しながら裏で更新する方式は、レイテンシと鮮度の交換を調整します。  
  期限切れの瞬間の集中を避ける効果もあります。  
  第17章のスタンピード対策と同じ原理です。


## ハンズオン：キー設計を変えてヒット率を見積もる


1. 配信対象のURLとアクセスパターンの例を用意します。
2. 現在のキー設計で、別々に保持されるバリエーションの数を数えます。
3. 不要な要素をキーから外す案を作り、バリエーション数の変化を計算します。
4. オリジンへの要求数がどう変わるか見積もります。


実在のCDNログが使える場合は、それで見積もりを検証してください。  
使えない場合は、想定の根拠を明記してください。


## 代償と判断


ヒット率を上げるためのキー削減は、誤った共有のリスクと引き換えです。  
長いTTLは、更新事故時の影響時間を延ばします。  
エッジでの処理を増やすと、運用と課金の複雑さが増します。


## 確認


- [ ] ヒット率がオリジン負荷を決める仕組みを説明できる

- [ ] キー設計とヒット率の関係を説明できる

- [ ] バージョン付きURLが失効の代替になる理由を説明できる


**演習：** 自分の関わる配信を1つ選び、キーに含まれる要素を列挙してください。  
外せそうな要素と、そのリスクを書いてください。
