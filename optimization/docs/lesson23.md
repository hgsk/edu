# 第23章 命令型とオブジェクト指向


[目次](../README.md) · [前の章：第22章 クラウドの会計](./lesson22.md) · [次の章：第24章 関数型、イミュータブル、遅延評価](./lesson24.md)


**この章で学ぶこと：** オブジェクト指向のデータ表現が運搬に与える影響を読み、データ指向設計とECSを対抗モデルとして評価できるようになります。


第VII部では、プログラミングモデルそのものを対象にします。  
オブジェクト指向は、現実のモデリングには強力ですが、データの並びについては無言です。  
その無言さが、運搬の観点では高くつくことがあります。


## 考え方


- **オブジェクトグラフはポインタの森：**
  参照でつながったオブジェクトは、走査のたびにランダムアクセスを生みます。  
  カプセル化は、レイアウトの最適化を外部から見えなくします。  
  1オブジェクトあたりの管理情報も、要素数が多いと無視できません。


- **データ指向設計：**
  データ指向は、処理の形から逆算してデータの並びを決める考え方です。  
  同じ種類の値を連続させ、必要なフィールドだけを運びます。  
  第5章のSoAは、その最も単純な形です。


- **ECSはその徹底形：**
  エンティティ、コンポーネント、システムへ分ける設計は、コンポーネント単位の連続走査を前提にします。  
  ゲームの大量要素の更新で威力を発揮します。  
  代償は、関係の表現と、デバッグのしにくさです。


- **使い分けの基準：**
  要素数が少なく、関係が主役の領域では、オブジェクト指向の表現力が勝ちます。  
  要素数が多く、同種の処理を繰り返す領域では、データ指向が勝ちます。  
  境界を引くことが設計であり、全面的な置き換えではありません。


## ハンズオン：同じ更新処理を2つのモデルで実装して比べる


1. 多数の要素へ同じ更新を行う処理を用意し、オブジェクトの配列で実装して時間を測ります。
2. フィールド別の配列で実装し直し、再測定します。
3. 要素数と、更新で触るフィールドの割合を変え、差の変化を観察します。
4. 読みやすさと変更のしやすさについても、両版を比べて記録します。


速度だけでなく、表現の代償まで含めて評価することが、この部の共通の作法です。


## 代償と判断


データ指向は、要素単位の振る舞いの記述を分散させます。  
ECSの導入は、既存コードとの境界管理を必要とします。  
モデルの選択は、チームの習熟とも無関係ではありません。


## 確認


- [ ] オブジェクトグラフが運搬に不利な理由を説明できる

- [ ] データ指向が勝つ条件と負ける条件を挙げられる

- [ ] ECSの前提と代償を説明できる


**演習：** 自分のコードの同種要素の集まりを1つ選び、データ指向化の可否を検討してください。
