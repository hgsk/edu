# 第26章 宣言型と、計算とスケジュールの分離


[目次](../README.md) · [前の章：第25章 所有権とマネージドモデル](./lesson25.md) · [次の章：第27章 並列と分散のモデル](./lesson27.md)


**この章で学ぶこと：** 宣言型のモデルが移動の決定を最適化器へ委ねる仕組みを理解し、実行計画と中間データの量でその働きを検証できるようになります。


宣言型は、「何を」を書き、「どう運ぶか」を系に委ねます。  
委ねることで最適化の余地が生まれ、同時に予測のしにくさも生まれます。  
この章では、委ね方の設計を扱います。


## 考え方


- **SQLの最適化器：**
  クエリの意味だけが与えられ、結合の順序や探索方法は最適化器が選びます。  
  統計情報の質が、選択の質を決めます。  
  実行計画を読むことは、委ねた相手の判断を監査することです。


- **Halideの分離：**
  Halideは、計算の定義と、実行のスケジュール（タイリングや並列化）を分けて書きます。  
  意味を変えずに運搬だけを最適化できるのが、この分離の価値です。  
  分離の思想は、他の分野の設計にも応用できます。


- **テンソル計算と融合：**
  即時実行では、演算ごとに中間テンソルが実体化し、メモリを往復します。  
  グラフコンパイルは、複数の演算を融合し、中間の運搬を消します。  
  中間データのバイト数を数えることが、この最適化の検証方法です。


- **委ねることの代償：**
  最適化器の選択は、データの分布が変わると裏切ることがあります。  
  ヒントや統計の維持は、委ねる側の責任として残ります。  
  全自動を信じず、計画を監査する姿勢が必要です。


## ハンズオン：中間データのバイト数を数える


1. 複数の演算を連ねた処理を用意し、即時実行での中間データの総量を見積もります。
2. 可能ならコンパイル実行に切り替え、時間とメモリの変化を記録します。
3. SQLの場合は、同じ問い合わせの実行計画を、書き方を変えて比べます。
4. 変化が見積もりと合うか検証します。


融合の効果は処理の形で大きく変わります。  
効かない例も、その理由と一緒に記録してください。


## 代償と判断


分離と自動化は、デバッグのときに「誰の判断か」を追いにくくします。  
スケジュールの最適化は、ハードウェア依存の調整を生みます。  
委ねた範囲が広いほど、監査の道具が重要になります。
