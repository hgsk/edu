# 第27章 並列と分散のモデル


[目次](../README.md) · [前の章：第26章 宣言型と、計算とスケジュールの分離](./lesson26.md) · [次の章：第28章 統一採否基準](./lesson28.md)


**この章で学ぶこと：** 共有メモリ、メッセージパッシング、データフローの各モデルが移動をどう扱うかを比較し、透過性の嘘とN+1問題を見抜けるようになります。


並列と分散のモデルは、移動を隠すか、露出させるかの選択です。  
隠すモデルは書きやすい代わりに、コストの発生箇所が見えません。  
この章では、モデルの敗北が観察できる形で現れる例を中心に扱います。


## 考え方


- **共有メモリモデル：**
  スレッドが同じメモリを見る前提では、通信は暗黙に起きます。  
  実体はコヒーレンスの交通であり、偽共有や競合として現れます。  
  書きやすさと、移動の見えにくさが一体です。


- **メッセージパッシングとアクター：**
  通信を明示的なメッセージにすると、コピーのコストは見えるようになります。  
  代償は、直列化とコピーの実費です。  
  場所の透過性をうたう実装でも、この実費は消えません。


- **データフローとストリーム：**
  処理をデータの流れとして表すモデルでは、シャッフルとウィンドウが移動と保持を露出させます。  
  ウィンドウの設計は、保持量の設計そのものです。  
  バックプレッシャーは、速度差を保持で吸収しすぎないための仕組みです。


- **透過性の嘘とN+1：**
  遠隔呼び出しをローカル呼び出しに見せるモデルは、距離のコストを隠します。  
  ORMの遅延読み込みがループと組み合わさると、クエリが要素数だけ発行されるN+1問題が起きます。  
  これはモデルの敗北であり、発行回数を数えることで検出できます。


## ハンズオン：N+1を検出して直す


1. 要素の一覧と、その詳細を遅延取得する処理を用意します。
2. 発行されるクエリや要求の回数を数えます。
3. 一括取得へ書き換え、回数と時間の変化を記録します。
4. 透過性が隠していたコストを、回数とバイト数で説明します。


回数を数える手段（ログやカウンタ）を用意すること自体が、この章の実践です。


## 代償と判断


明示的な通信は、コード量と設計の負担を増やします。  
一括取得は、不要なデータまで運ぶリスクと引き換えです。  
透過性を捨てる判断は、抽象化の利便性との交換です。


## 確認


- [ ] 共有メモリの暗黙の通信を、コヒーレンスとして説明できる

- [ ] 明示的な通信の利益と実費を説明できる

- [ ] N+1の発生条件と検出方法を説明できる


**演習：** 自分のコードで、ループの中から呼ばれる取得処理がないか点検してください。  
ある場合は、発行回数の見積もりを書いてください。
