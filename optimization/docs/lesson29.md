# 第29章 アンチパターン集


[目次](../README.md) · [前の章：第28章 統一採否基準](./lesson28.md) · [次の章：第30章 総合演習](./lesson30.md)


**この章で学ぶこと：** 保持と移動にまつわる典型的な失敗を診断し、症状から原因の層と技法を特定できるようになります。


失敗の形は、成功の形よりよく再現します。  
この章では、現場で繰り返し現れるアンチパターンを、診断の手順と一緒に 一覧化します。


## 考え方


- **無制限なメモ化：**
  入力の種類が増えるたびに表が育ち、やがて容量の崖に当たります。  
  症状は、長時間運転でのみ現れる遅さとメモリの単調増加です。  
  追い出し方針のないメモ化は、リークと区別がつきません。


- **巨大なプールと低い占有率：**
  安全を見込んで大きくしたプールが、使われないまま容量を占有します。  
  症状は、起動直後からの高いメモリ使用量と、他の処理の圧迫です。  
  占有率の計測がないプールは、ほぼこの状態にあります。


- **二重キャッシュと層の競合：**
  同じデータを複数層で保持すると、容量と無効化の両方が二重になります。  
  症状は、ヒットしているのに全体が速くならない状態です。  
  保持の棚卸しと、層をまたぐ予算の一元化が対策です。


- **早すぎるキャッシュ：**
  律速を特定する前にキャッシュを入れると、複雑さだけが残ります。  
  症状は、保守コストの増加と、効果の説明できないコードです。  
  計測前の最適化は、ほぼこのパターンに分類できます。


## ハンズオン：悪い設計例を診断する


1. 症状だけが書かれた事例を1つ用意し、どのパターンに当たるか当てます。
2. 診断を確かめるために追加で測るべき項目を挙げます。
3. 処方として、縮小、廃止、再設計のどれを選ぶか決めます。
4. 処方の効果を確かめる測定方法も設計します。


事例は自分の経験から作っても構いません。  
症状と数値を分けて書くことがコツです。


## 代償と判断


パターンへの当てはめは、個別の事情を見落とす危険があります。  
診断は仮説であり、測定で裏を取るまで処方を確定しません。  
廃止の処方は、導入した人の意図を尊重しながら進める必要があります。


## 確認


- [ ] 4つのアンチパターンの症状を説明できる

- [ ] 症状から追加測定を設計できる

- [ ] 縮小、廃止、再設計の選択基準を説明できる


**演習：** 自分のシステムから、アンチパターンに近い箇所を1つ探してください。  
診断のための測定項目を書いてください。
